# 0009 TUI and the manager's overview

Status: Proposed (spike DIPO-6, 2026-10-10).

## Context

The TUI is the first client (0001). It is how the maintainer runs an office as a manager (vision section 8, 0011 item 10). At any moment it must answer four questions for one office: who works on what, how it is going, what needs doing, and whether it is cost efficient. The maintainer must be able to step into running work and switch between offices.

Fixed by earlier decisions:

- **0004:** TypeScript on Bun 1.4, one binary `dipo`. `packages/tui` imports only `contract` and `client`; an oxlint rule forbids `engine` and `daemon`. Ink was chosen by the maintainer; this spike confirms it with a prototype plan, with OpenTUI as the fallback.
- **0005:** commands, reads and events are the only interface. Views such as column, health and waiting-on-maintainer are derived in the engine, and clients never compute status. Phase and signal names are provisional, and this ADR sets the final ones. Capability flags hide features, `stream.resetRequired` forces a fresh snapshot, and commands with `confirm: true` are confirmed by every client.
- **0006:** one daemon for all offices. The selected office is client state. Any client command starts the daemon when it is not running. Daemon states are `starting`, `recovering`, `running`, `draining` and `safe`. A worker can be in follow-only mode (host alive, socket gone), and then it cannot be steered. The browser listener is off by default.
- **0012:** lifecycle Draft, Refined, Ready, In Progress, In Review, Parked, Done, Removed. `on-hold` is a park reason. Ready gate failures are messages prefixed with a rule id.
- **0013, 0015, research:** run knowledge comes from the scan. We borrow ideas from other tools but use our own words, so the placeholder terms in research section 6.8 get final names here. Ideas 2 (evidence labels), 9 (health states) and 20 (views built by code) belong to this spike.

Facts checked on 2026-10-10:

- `ink` 8.0.0 was released 2026-10-03. It needs `node >=22` and a `react >=19.3` peer, and it lays out with `yoga-layout ~3.2.1` [1][2]. Changes from 7.x to 8.0 that matter here: incremental rendering skips unchanged line prefixes, which means less flicker; screen-reader output was fixed; `render()` accepts any Node stream; and `useInput` no longer receives unrecognised control sequences. 7.x added `alternateScreen`, `useWindowSize`, `usePaste` and `suspendTerminal()` [2].
- `yoga-layout` 3.2.1 loads its WebAssembly from a base64 ES module with top-level await [3]. There is no separate `.wasm` file to embed, but `bun build --compile` must handle the top-level await.
- `ink-testing-library` 4.0.0 has peer `@types/react >=18` and was built against Ink 5. It wraps Ink's `render` with fake stdin, stdout and stderr (100 columns, `debug: true`) and exposes `lastFrame`, `frames`, `stdin.write`, `rerender`, `unmount` and `cleanup` [4][5]. Nobody documents it working with Ink 8 or under `bun test`, so this is unverified.
- Ink inside a Bun-compiled binary: Claude Code is a `bun build --compile` binary, and its stack traces show Ink's raw-mode handler under `/$bunfs/root/...` [6]. This shows an Ink-based renderer can run from a compiled Bun binary. Whether it is unmodified Ink 8 is unverified.
- Known issues: Ink throws "Raw mode is not supported" when stdin is not a TTY. The fix is to check `isRawModeSupported` first [6][7]. A downstream project found that under Bun, `process.stdin.isTTY` can become falsy after an Ink instance unmounts and calls `setRawMode(false)`, which leaves the next `render()` deaf to keys. Its workaround passes a stdin proxy that pins `isTTY` [8]. It is not confirmed on Bun 1.4.
- Ink's README states it does not accept fully AI-generated pull requests [9], so we must patch around problems ourselves rather than send fixes upstream.
- None of the above was run in this spike. The local Bun is 1.3.5 and this session had no package registry access. The prototype below is the verification step.

## Options

| | A. Ink 8 (chosen) | B. OpenTUI (`@opentui/react`) | C. Own renderer on raw ANSI |
|---|---|---|---|
| Model | React and Flexbox (Yoga) | React or Solid on a native core | Hand-written diffing and layout |
| Maturity | 8 major versions, widely used, one maintainer | 0.x, Bun-first, used by OpenCode | None |
| Bun and compiled binary | Expected; Claude Code is evidence; prototype confirms | Bun-first; the native library must load from the compiled binary (unverified) | Certain |
| Testing under `bun test` | `ink-testing-library` or a 60-line harness on Ink 8 streams | Its own test renderer (unverified) | Our own |
| Shared with a web client | Same React, hooks and store; only leaf components differ | Same React | Nothing |
| Risk | Full-tree re-render cost on busy screens; raw-mode edge cases | API churn before 1.0; native binary per target | Months of work, accessibility handled by us |

## Decision

### 1. Ink 8 is confirmed, subject to a prototype

The first `tui` story begins with a throwaway prototype on a scratch branch that is never merged. Pin Bun 1.4.2, `ink@8.0.0`, `react@19.3.x` and `ink-testing-library@4.0.0`, then check:

1. **Bun runtime.** Render the overview from contract-typed fixtures: 40 stories, 8 agents, usage updates at 1 Hz and an output tail at 4 Hz, at 120x40 and 80x24. Incremental rendering is opt-in in Ink 8, so measure with `incrementalRendering: true` and with it off, and keep the better one. Pass if there is no visible flicker in iTerm2, Terminal.app, a Linux VTE terminal and tmux, and the process idles below 5% of one core.
2. **Compiled binary.** `bun build --compile` for darwin-arm64 and linux-x64, then run the binary in a real PTY (through `Bun.spawn` with `terminal`). Pass if: yoga's top-level await loads; raw-mode keys work; resize (SIGWINCH) reflows; the alternate screen is entered and left; the terminal is restored on `q`, Ctrl+C, SIGTERM and an uncaught error; and an unmount followed by a new mount still gets keys (the `isTTY` issue [8]).
3. **Tests.** `bun test` with `ink-testing-library`: render, `stdin.write` arrow keys and letters, `lastFrame()` with ANSI stripped. If 4.0.0 fails against Ink 8 (types or stream shape), write our own harness of about 60 lines: Ink 8 `render()` over `PassThrough` streams with fixed columns. Either way the test API stays `render`, `press`, `frame`.
4. **No TTY.** `dipo tui` with piped stdin exits with a clear message (`isRawModeSupported`) and a non-zero code instead of an Ink stack trace.

**Fallback trigger:** if check 2 fails with no workaround found within one day, or check 1 fails after the mitigations in section 9, move to OpenTUI's React renderer. Views, store and tests above the leaf components stay as they are. Record that as an amendment here.

### 2. Thin client

The TUI uses only the public interface of 0005: commands, reads and events, typed by `contract` and carried by `client`. It imports nothing else from this repository; the 0004 oxlint rule fails `verify` if it tries.

`dipo tui` goes through `client`. It sends `engine.hello`, then subscribes to the software stream. For the selected office it reads `office.snapshot` and then subscribes after its cursor (0005 section 8). Its state is an `OfficeStore` from `client`, which `web` shares (section 10). The store takes the snapshot, applies events by subject (`key`, `run`, `gate` and so on), drops duplicates by cursor and handles reset. It replaces views. It never computes column, health, phase, evidence or cost. The TUI renders `StoryView`, `WorkView`, `GateView`, `QuestionView`, `TestView` and the reads proposed in section 8, and nothing else. Keys and actions come from `commands.describe`, `story.parked.actions` and capability flags. The overview, desk, digest and cost views are built by engine code from facts with no model call (idea 20). A model summary exists only when the maintainer asks the conversation layer (M5).

### 3. Our own vocabulary

**Evidence labels** (idea 2). Every value the engine puts in a view carries one label:

| Label | Meaning | Examples |
|---|---|---|
| `checked` | The engine measured or did it itself | phase, loop, verify result, elapsed time, process state, git state, gate decisions |
| `claimed` | The worker, its CLI or the reviewer said so | criteria ticked, tokens from stream-json, "I am done", reviewer verdict |
| `estimated` | A rule computed it from partial facts | cost from the pricing catalog, `quiet`/`stuck`, trends, time to budget |
| `none` | No fact yet; the value is shown as `?` and never guessed | plan-limit usage before DIPO-5 supplies it |

Display: `checked` values show plain. A `claimed` value gets a trailing `*` and an `estimated` value a leading `~`. A `none` value is `?`. A legend sits in the footer, and `e` toggles full words (`12/15 claimed`). Labels travel in an optional `evidence` field, which the engine sends only with the `evidence` capability flag. Without it the TUI shows plain values, with no markers and no legend.

**Phases** (final, replacing 0005's provisional list; an open enum so later roles can add phases): `setup` (worktree, install), `build`, `verify`, `review`, `test` (waiting for the maintainer's test), `merge`.

**Watchdog signals** (`work.observed`, final; open enum): `no-output` (no line for `timeouts.workerStallMinutes`), `same-failure` (the same verify failure signature twice in a row, or three equal permission denials in a run, as in draft 0008), `input-wait` (the CLI waits for a permission or input), `plan-limit` (the account's plan limit was hit and the run waits for the reset, 0008 section 7), `host-lost` (the worker host died with no exit file), `follow-only` (0006 decision 8). Renames for DIPO-5 (draft 0008 section 3 uses the 0005 provisional names): `silent` to `no-output`, `waiting-input` to `input-wait`, `repeating-failure` to `same-failure`; `plan-limit` keeps its name.

**Health states** (idea 9). A fixed set of eight states. This tightens 0005's `z.string()` before 1.0, which 0005 open question 6 allows. It is an open enum on the wire: a client shows an unknown value as its plain word, with no glyph or colour. The engine derives health from facts in this precedence order. Time-based states are facts too: the engine watchdog writes a `work.observed` fact when a threshold is crossed, so health changes only through events. `lastOutputAt` is for display only.

| Health | Rule (thresholds in office config `timeouts`, as in 0008) | Text and glyph |
|---|---|---|
| `lost` | `host-lost`, or a worker exit not yet processed | `LOST !!` |
| `asking` | open question, `input-wait`, or a gate waiting on the maintainer for this run | `ASKING ?` |
| `limited` | `plan-limit`: waits for the reset, no action needed | `limited %` |
| `paused` | `work.pause` took effect | `paused =` |
| `looping` | `same-failure`, or loop >= cap - 1 | `looping @` |
| `stuck` | `no-output`: nothing for `workerStallMinutes` (default 20), host alive | `stuck ~` |
| `quiet` | no output for `workerQuietMinutes` (default 3, new key) | `quiet .` |
| `busy` | output within `workerQuietMinutes` | `busy >` |

Health, phase and lifecycle are separate columns, so "stuck in verify" reads as two words. A follow-only run adds the tag `[follow]` and greys out steering, with the reason shown in the footer.

**Waiting on the maintainer:** the column and view is called **Your desk**. It holds open questions, gates waiting on the maintainer, flagged stories in `test`, and parked stories. On-hold stories are listed separately under "Held by you" so they do not nag. The count comes from `OfficeSummary.waitingOnMaintainer`.

**Queue columns** (`StoryView.column`, engine-derived): `draft`, `refined`, `ready`, `waiting` (Ready but a dependency is not Done; the reason lists the ids), `running`, `review`, `desk`, `held`, `done`.

### 5. Interventions

Every action is one command from 0005. The TUI fills `origin: "tui"` and a fresh `requestId`. Confirmation follows `commands.describe.confirm`. The TUI asks for typed confirmation (the user types the story id) only when the proposed `irreversible` flag (section 8) is set.

| Action | Key | Command | Confirmation |
|---|---|---|---|
| answer | `a` | `work.answer { question, text }` | none; Enter sends |
| steer | `s` | `work.steer { story, text }` | none; disabled when follow-only |
| pause | `p` | `work.pause` | none (reversible) |
| resume | `r` | `work.resume { story, note? }` | none; a safe-mode refusal shows `scheduling.off` |
| reassign | `R` | `work.reassign { story, role?, tier? }` | yes: shows old and new role, tier and model |
| stop | `X` | `work.stop { story, note? }` | yes: "worker ends, branch kept, story parks as stopped" |
| discard | `Shift-D` | `work.discard { story, note }` | yes, typed: "deletes worktree and branch" |
| hold | `h` | `story.hold { story, note }` | none; note required |
| drop | `d` | `story.drop { story, deleteBranch }` | yes; typed if `deleteBranch` |
| approve / reject gate | `y` / `n` | `gate.approve` / `gate.reject { note }` | reject: yes, note required |
| test | `t`, then `P` / `F` | `test.start`, `test.record { result, note? }` | fail needs a note |
| run | `u` in queue | `work.run { stories? }` | none; the result lists started and skipped with reasons |
| resume scheduling | `S` in banner | `daemon.resumeScheduling` | yes |
| forget office | `F` in switcher | `office.forget { office }` | yes: "removes it from the list; the repository is untouched" |

Errors show `message` in the footer. A retryable error (`run.hostAlive`, `engine.recovering`) offers `Ctrl-R` retry, which reuses the same `requestId`. `changed: false` shows "already so". After a reply the TUI waits until its stream passes the reply cursor before it marks the action done (read-your-writes).

### 6. Keys and navigation

Global: `1` to `5` views, `o` offices, `Tab` and `Shift-Tab` next and previous panel, `j`/`k` or arrows move, `Enter` drill in, `Esc` back or cancel, `/` filter, `:` command palette (every command in `commands.describe` the flags allow, so nothing is reachable only by a hidden key), `e` evidence words, `?` help, `q` quit (a second `q` within 2 s, or `Esc` from home). Uppercase keys are for actions that end or replace work. A view may bind a letter that a global key also uses (`F` forgets an office in the switcher, `F` fails a test in the checklist), and then the view's binding wins. The footer always shows the active one. Text prompts take `Enter` to send and `Esc` to cancel; pasting (`usePaste`) inserts literally. No action fires on a single keypress without its target being visible on screen.

### 7. Connection and daemon states

- **Start:** `dipo tui` autostarts the daemon through `client` (0006), shows `starting…`, and opens the office of the current directory or the last one used. It does not need the browser listener.
- **Disconnected:** the header shows `OFFLINE since 12:04 – view frozen`. Values keep their last state with an age. Action keys are disabled and typed drafts are kept. The client reconnects with backoff (0.5 s, doubling to 5 s) and subscribes after the last cursor. A command sent before the disconnect is re-sent with the same `requestId`, which is safe because commands are idempotent. "Live" returns after `stream.mark { caughtUp }`.
- **`stream.resetRequired`:** the store drops the view, re-reads `engine.hello` and `office.snapshot`, and shows `view reloaded (history gap)` once. The cursor of the selection is kept by `key`.
- **Daemon `starting` or `recovering`:** the banner reads `Daemon recovering – office data after reconcile`. Reads that fail with `engine.recovering` are retried on `daemon.state` to `running`. `draining` reads `Daemon stopping – will reconnect`. `safe` reads `Scheduling off after repeated crashes – [S] resume scheduling`. Work that would schedule shows why it is refused.
- **`contract.unsupported`:** shows the daemon's and the client's versions and suggests `dipo daemon restart`.

### 8. Cost efficiency and proposed contract additions

The cost view (`5`) groups usage by story, role or tier (`g` cycles) for today, 7 days or 30 days (`w` cycles):

```
 Cost · by tier · 30 days               unit: tokens (cost ~ from catalog)
 TIER STORIES AVG/BUDGET  WITHIN  OVER(parked)  AVG LOOPS  TREND (wk)
 S    14      31%          14/14   0             1.4        ▁▂▂▁  -8%
 M    9       64%          8/9     1             2.9        ▃▄▆▅ +12%
 L    2       71%          2/2     0             4.0        ▅▅    n/a
 shared plan limit: ? (none)   day spend ~$3.10 of ~$12 alert at 80%
```

Trends are numbers next to the sparkline, so meaning never depends on its shape. Dollar amounts are always `estimated`, and on a subscription they are notional.

Additive minor changes to the 0005 contract (minor version bump, flags in brackets):

- `Evidence = z.enum(["checked","claimed","estimated","none"])` (closed). Optional `evidence?: Record<string, Evidence>` on `WorkView`, `StoryView`, `OfficeSummary` and every read below, keyed by field path. [`evidence`]
- `Health` as the open enum in section 3, replacing `z.string()`. Signals and phases as above. `WorkView.signals` and `WorkView.lastOutputAt` (display only).
- `Usage.budgetShare: number`, engine-derived (used divided by limit, with its evidence).
- `OfficeSummary.daySpend?: { share: number, alert: boolean }`, engine-derived from the spend alerts of idea 6 (M1). The switcher hides it until that lands. [`usage.alerts`]
- `story.parked.actions` may include `work.discard` for parked stories with a branch.
- `StoryView.waitingOn?: StoryId[]` and `StoryView.gateMessages?: string[]` (the first Ready gate failures, for Refined).
- Read `office.usage { office, groupBy: "story"|"role"|"tier", window }`, which returns engine-derived totals, budget share, within or over counts, average loops and weekly buckets. [`usage.report`]
- Read `office.digest { office, since }`, which returns code-built "since you left" counts and lines. [`digest`]
- `commands.describe` gains `irreversible: boolean` (true for `work.discard`, and for `story.drop` with `deleteBranch`).


### 9. Narrow terminals, performance and accessibility

- **Width.** At 120 columns or more, everything shows. From 80 to 119, the model, turns and trend columns are dropped and role is shortened (`dev`, `rev`). From 60 to 79, each agent is a two-line card with story, health word, phase on line one and AC, loop and budget % on line two. Below 60 columns or 16 rows, one list shows story, health and desk count, plus "widen for detail". There is never horizontal scrolling. Long titles are truncated with `…` and shown in full in detail.
- **Rendering.** Alternate screen by default (`--inline` turns it off). Output panes keep only the visible lines in React state and fetch the rest with `work.outputRange`. The store batches events per animation frame (at most 10 Hz). Rows are memoised by `key`.
- **No colour-only signals.** Every state is a word plus an ASCII glyph. Colour is extra. `NO_COLOR` and `--no-color` are honoured. `--ascii` replaces box drawing and the sparkline with ASCII. Tests assert on frames with ANSI stripped, so meaning survives monochrome.
- **Screen readers.** Ink's screen-reader mode (fixed in 8.0 [2]) with `aria-label` on rows, such as "DIPO-24, verify, looping, loop 2 of 3". Nothing blinks, and the spinner is optional.

### 10. Web and 3D clients follow the same path

A `packages/web` client (0004, research section 8) connects through the loopback listener, which is off by default; `dipo web` starts it (0006 decisions 10 and 11). It sends the same `auth` frame and then the same `engine.hello`, `office.snapshot`, subscribe and reads, and it uses the same `OfficeStore` from `client`. Views, evidence, health, desk and cost arrive ready-made, so web and TUI cannot disagree. React components above the leaves (store hooks, view models, action maps from `commands.describe`) can move from `tui` into a shared package once web exists. A 3D office is a pure function of the store: an agent is a `WorkView`, posture follows `health`, an `asking` agent raises a hand, and desk items stack on the maintainer's desk. The dense overview stays the primary view (research section 4). A desktop app is a Tauri or Electron shell around `packages/web`, using the same auth, handshake and store.

## Consequences

- One rendering stack and one store for TUI and web. Status rules stay in the engine.
- The contract gains the minor additions in section 8. DIPO-4 and DIPO-5 must record lastOutputAt, signals and evidence per fact; DIPO-5 decides which usage numbers are `claimed` and adopts the signal renames in section 3.
- The prototype is a gate on the first `tui` story. If it fails, OpenTUI replaces Ink at leaf level and this ADR is amended.
- We depend on a single-maintainer library that will not take AI-written fixes. Workarounds (stdin proxy, own test harness) live in `packages/tui`.
- Health thresholds and the alert level become office configuration (DIPO-14 format).

## Open questions for the maintainer

1. **Names:** are `checked/claimed/estimated/none`, the eight health states, the phases `setup/build/verify/review/test/merge` and "Your desk" right?
2. **Contract additions** in section 8: accept them as a minor amendment to 0005?
3. **Health defaults:** quiet after 3 min and stuck after 15 min without output? Is "looping" at loop >= cap - 1 too eager?
4. **Typed confirmation** for discard, and for drop with branch deletion: yes, or is a normal yes/no enough?
5. **Cost unit:** tokens first with estimated dollars next to them, or dollars first? On the Max subscription dollars are notional.
